Introducción

El video Supabase, Tutorial Práctico y Overview (REST API), del canal Fazt Code, presenta Supabase como una alternativa a Firebase: un servicio en la nube donde uno crea una cuenta y obtiene un backend con base de datos, autenticación y almacenamiento de archivos, sin escribir código para armarlo.

El autor crea un proyecto desde cero, arma una tabla de productos con tres registros (laptop, monitor y mouse gaming) y comprueba que Supabase genera una REST API a partir de esa tabla. Después prueba la API con Postman y explica por qué hace falta activar la seguridad a nivel de fila (RLS). En esta página explico los conceptos, respondo el cuestionario y muestro un ejemplo práctico.

Conceptos fundamentales

Supabase

Servicio en la nube, alternativa a Firebase, que ofrece base de datos, autenticación y almacenamiento (Storage). Se registra con una cuenta de GitHub y se configura desde un panel web.

Base de datos PostgreSQL

A diferencia de Firebase, que usa una base NoSQL, Supabase usa una base SQL (Postgres). Los datos se guardan en tablas con columnas y filas.

REST API automática

Cada tabla que se crea genera sus propios endpoints, con documentación incluida. Se basa en PostgREST, y permite leer, escribir, actualizar y eliminar datos mediante peticiones HTTP.

API key y cabeceras

Para consultar la API hay que enviar la clave anon public en la cabecera apikey y la misma clave, precedida de Bearer, en la cabecera Authorization. Sin ellas, la API devuelve un error.

RLS y políticas

Row Level Security son reglas extra sobre las tablas, parecidas a las Firebase Rules. Con RLS activado y sin políticas, la API devuelve una lista vacía. Con una política se define quién puede hacer cada operación.

Biblioteca cliente

Módulo que se instala en la aplicación y hace de intermediario con la REST API, con funciones más simples. En el video está disponible la de JavaScript, y las de Python y Dart estaban en versión alfa y beta.

Cuestionario resuelto

Toca cada pregunta para ver la respuesta.

1. ¿Cuál es el tema principal del video? Explica de qué trata.

El tema principal es Supabase, una alternativa a Firebase, y cómo su base de datos genera automáticamente una REST API. El video muestra cómo crear la cuenta y el proyecto, cómo crear una tabla y cargar datos, y cómo consultar esos datos desde un cliente REST.

También trata la seguridad: explica por qué no conviene dejar la API abierta y cómo las reglas RLS controlan el acceso.

2. ¿Qué problema o necesidad tecnológica se aborda?

La necesidad es tener un backend (base de datos, usuarios, archivos y una API) sin programarlo desde cero. Supabase lo configura en unos tres minutos desde un panel, sin escribir código.

Otro problema que se aborda es la seguridad: si una aplicación usa la URL y la clave públicas, cualquiera podría obtenerlas desde el front-end y hacer operaciones de lectura, escritura o actualización. Para eso se usa RLS.

3. ¿Cuáles son los cinco conceptos más importantes? Define cada uno.
  1. Supabase: servicio en la nube, alternativa a Firebase, con base de datos, autenticación y almacenamiento.
  2. PostgreSQL: base de datos SQL donde se guardan los datos en tablas, filas y columnas.
  3. REST API: interfaz que se genera sola al crear una tabla y permite leer, escribir, actualizar y eliminar datos por HTTP.
  4. API key: clave (anon public) que se envía en las cabeceras apikey y Authorization para poder consultar la API.
  5. RLS (Row Level Security): reglas que se agregan sobre las tablas para decidir qué operaciones se permiten, según políticas.

5. ¿Qué procedimientos o pasos se explican? Preséntalos en orden.
  1. Entrar a Supabase.com y registrarse con una cuenta de GitHub.
  2. Crear un proyecto con New project: elegir el plan gratuito, poner un nombre y una contraseña.
  3. Esperar unos tres minutos a que se configure el backend.
  4. En Database, crear una tabla nueva (products) con una columna name de tipo VARCHAR y requerida.
  5. En Table editor, insertar filas: laptop, monitor y mouse gaming.
  6. En la sección API, abrir la tabla y copiar el endpoint de Read rows desde la pestaña Bash.
  7. En Postman, hacer la petición. Sin clave da error; al agregar las cabeceras apikey y Authorization devuelve las tres filas.
  8. Activar RLS (Enable RLS): la misma petición devuelve una lista vacía.
  9. Crear una política nueva con la plantilla de lectura para todos: la petición vuelve a devolver los datos.
  10. Probar un POST: da error, porque no hay una política que permita escribir.
6. ¿Qué ejemplos prácticos aparecen? Explica uno detalladamente.

El ejemplo principal es una tabla de productos (products), con tres filas: laptop, monitor y mouse gaming. Lo explico en el orden en que ocurre en el video:

1. Crear la tabla. En Database se crea products con una descripción y una columna name (VARCHAR, sin permitir nulos). Supabase agrega solo id y created_at.

2. Consultar la API. Se copia el endpoint de lectura y se envía desde Postman. Sin clave responde con un error que indica que falta la API key. Con las dos cabeceras responde con un arreglo de tres objetos, cada uno con nombre, id y fecha de creación. El equivalente en cURL es:

curl 'https://TU_PROYECTO.supabase.co/rest/v1/products?select=*' \
  -H "apikey: TU_CLAVE_ANON" \
  -H "Authorization: Bearer TU_CLAVE_ANON"

3. Activar RLS. Al activarlo, la misma petición no da error pero devuelve []. Las credenciales son correctas, pero no existe ninguna regla que autorice la lectura.

4. Crear la política. Con la plantilla «habilitar acceso de lectura para todos» la tabla vuelve a ser legible. La política equivale, en esencia, a:

create policy "Enable read access for all users"
on products for select
to public
using (true);

5. Probar escribir. Un POST falla, y eso es lo esperado: la política solo permite leer.

7. ¿Qué conocimientos previos son necesarios para comprender lo explicado?
  • Qué es una base de datos, una tabla, una fila y una columna, y la diferencia entre bases SQL y NoSQL.
  • Qué es una API REST: URL, métodos HTTP (GET, POST) y cabeceras.
  • El formato JSON, porque la API responde con arreglos de objetos.
  • Haber visto Firebase u otro servicio similar, porque el autor lo compara varias veces.
  • Usar un cliente como Postman, o cURL si se sabe usar la consola.
8. ¿Qué ventajas o beneficios ofrece la tecnología o procedimiento?
  • No hace falta programar el backend: el proyecto se configura desde un panel, en unos tres minutos.
  • La REST API se genera sola al crear cada tabla, con su documentación y ejemplos.
  • Base de datos SQL (Postgres), con tipos de datos variados.
  • Todo en un solo lugar: base de datos, autenticación (usuario y contraseña, Magic Link, OAuth) y almacenamiento de archivos.
  • Funciona con cualquier lenguaje o framework que pueda hacer peticiones HTTP, y también hay biblioteca para JavaScript y templates listos.
  • Plan gratuito para empezar a probar.
9. ¿Qué dificultades, errores o precauciones deben considerarse?
  • Claves expuestas: si una aplicación usa solo la URL y la API key, cualquiera puede obtenerlas desde el front-end y hacer lecturas, escrituras o actualizaciones. Por eso no hay que confiar solo en la clave.
  • RLS activado sin políticas: la API devuelve una lista vacía sin mostrar ningún error, y eso puede confundir.
  • Las escrituras necesitan más control: la lectura puede ser pública (por ejemplo, los productos de una tienda), pero crear, actualizar y borrar deberían exigir un usuario autenticado y, a veces, un rol.
  • Cabeceras correctas: falta de apikey da error, y Authorization debe llevar la palabra Bearer y un espacio antes de la clave.
  • Confusión inicial en el panel: las tablas se crean en Database, pero las filas se editan en Table editor.
  • Tiempo de creación: el proyecto tarda unos tres minutos en estar listo, algo más que en Firebase.
10. ¿Cómo aplicarías lo aprendido en un proyecto informático real?

Lo usaría para un sistema de inventario de equipos de un laboratorio de informática, parecido al ejemplo de productos. Crearía una tabla equipos con nombre, estado y ubicación, y una página con HTML, CSS y JavaScript que liste los equipos con una petición GET.

Siguiendo lo del video, activaría RLS: dejaría la lectura pública mediante una política, y permitiría crear, modificar o borrar equipos solo a usuarios autenticados.

11. ¿Qué parte del video consideras más importante y por qué?

Considero más importante la parte de RLS. Primero el autor muestra que con la clave se leen los datos, y después advierte que esa clave puede verla cualquiera en el front-end. Al activar RLS, la misma petición devuelve una lista vacía, y con la política vuelve a funcionar.

Me parece clave porque enseña que una API que funciona no es lo mismo que una API segura.

12. ¿Qué conocimientos nuevos adquiriste y cómo los explicarías a otra persona?

Aprendí que al crear una tabla en Supabase se genera automáticamente una REST API, que se prueba con Postman usando dos cabeceras, y que la seguridad se maneja con RLS y políticas.

Se lo explicaría así: «Supabase es como Firebase, pero con una base de datos de tablas. Cuando creás una tabla, ya tenés una dirección web para pedir sus datos. Esa dirección pide una clave, y además podés poner reglas que dicen quién puede leer o escribir».

Aplicación práctica

Este es el mismo procedimiento del video (la petición de lectura que se hace en Postman), pero hecho desde una página web con JavaScript. Así la lista de productos se muestra en la propia página.

const URL_API = "https://TU_PROYECTO.supabase.co/rest/v1/products?select=*";
const CLAVE = "TU_CLAVE_ANON";

async function mostrarProductos() {
  const respuesta = await fetch(URL_API, {
    headers: {
      apikey: CLAVE,
      Authorization: "Bearer " + CLAVE
    }
  });
  const productos = await respuesta.json();
  productos.forEach(p => console.log(p.name));
}

mostrarProductos();

Para que esto devuelva datos, la tabla necesita una política de lectura (paso 9 del procedimiento). Con RLS activado y sin política, el resultado sería una lista vacía.

Filtros disponibles

La sección API también documenta filtros para las consultas. Permiten pedir solo las filas que cumplan una condición:

  • si un valor es igual a otro;
  • si es mayor o menor;
  • si es mayor o igual, o menor o igual;
  • si un texto se parece o se incluye, o si no se parece.

Conclusión personal

Este video me mostró que se puede tener un backend completo sin programarlo desde cero. En pocos minutos pasé de una cuenta vacía a una tabla con datos y una API que cualquier aplicación puede consultar.

Lo que más me quedó es que la comodidad exige cuidado: una clave pública en el front-end puede ser vista por cualquiera, y por eso las reglas RLS son indispensables. Esto me sirve para mis proyectos de la materia, porque puedo guardar datos reales en mis páginas web y publicarlas con una base de datos en línea.
